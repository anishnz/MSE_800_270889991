# Part F: Challenge (Optional)

## Problem Statement

1. Add a rule to `create_booking` that rejects bookings starting in the
   past, with its own exception class.
2. Add a logging call inside a catch block so each failed booking
   attempt is written to `errors.log` with a time stamp.
3. Explain in two sentences why `except: pass` would be dangerous in the
   booking save routine.

## Requirements

1. A new exception, `BookingInPastError(RentalError)`, raised when
   `start` is earlier than today.
2. Every failed booking attempt in the menu loop is logged to
   `errors.log`, with a timestamp, in addition to the message shown to
   the user.
3. A short written answer to the `except: pass` question (see below and
   `QUESTION_AND_ANSWER.txt`).

## How It Works

- `booking.py` is Part D's module plus one more check and one more
  exception class:

  ```
  RentalError
  +-- InvalidDateRangeError
  +-- CarNotFoundError
  +-- CarUnavailableError
  +-- BookingInPastError      <- new in Part F
  ```

  `create_booking()` now takes an optional `today` parameter (defaults
  to `date.today()`), checked *before* the date-range check - a start
  date that is already in the past is a problem regardless of whether
  `end` comes after it. Passing `today` explicitly is what lets this
  rule be tested without depending on the real calendar date.
- `logging.basicConfig(filename="errors.log", level=logging.ERROR, format="%(asctime)s %(levelname)s %(message)s")`
  is set up once, when the module is imported. `%(asctime)s` in the
  format string is the timestamp.
- Inside each `except` block in the menu loop, `logging.error(...)`
  writes one line to `errors.log` (car ID, the dates typed, and the
  error message), and `print(...)` still shows the same failure to the
  user on screen - both happen for every failed attempt.
- **Why `except: pass` would be dangerous in the booking SAVE routine**
  (the part that actually writes a confirmed booking to disk or a
  database), in two sentences: `except: pass` silently swallows *every*
  error - including ones that have nothing to do with the booking
  itself, such as the disk being full or a dropped database connection
  - so a booking the customer was already charged for can simply vanish
  with no record that saving it ever failed. Because nothing is logged
  or re-raised, there is no way to notice the problem, show the
  customer an honest error, or investigate later - the failure is not
  handled, it is just hidden.

## Running the Program

```bash
python main.py
```

### Sample Session (today = 2026-10-04)

```
Car ID: C001
Start date (YYYY-MM-DD): 2020-01-01
End date (YYYY-MM-DD): 2020-01-05
Booking failed: Start date (2020-01-01) is in the past; today is 2026-10-04.

Car ID: C001
Start date (YYYY-MM-DD): 2030-01-01
End date (YYYY-MM-DD): 2030-01-05
Booking confirmed for C001: 4 day(s), total fee $180.00

Car ID: quit
```

### Resulting `errors.log`

```
2026-10-04 11:33:02,342 ERROR Booking failed for car C001 (2020-01-01 to 2020-01-05): Start date (2020-01-01) is in the past; today is 2026-10-04.
```

(Every failed attempt - past date, unknown car, unavailable car, bad
date range - adds one more timestamped line; only successful bookings
are not logged, since nothing failed.)
